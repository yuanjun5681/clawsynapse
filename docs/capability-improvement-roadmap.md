## 1. 目标与范围

下一步优先从“能发消息、能调用 Agent”提升为“请求可识别、输出可流式传递、执行可追踪、失败不误报、重启可恢复”。

本文关注通用 Agent 通信能力，不将 ClawSynapse 扩展为业务审批系统、设备安全控制层或 Agent 调度平台。

相关规划：

- [面向 Camind 的能力提升规划](./camind-capability-improvement-plan.md)：生产设备通道的安全、可靠交接及业务职责。
- [Harness 移动端 NATS 接入设计](./mobile-nats-access.md)：手机与 Harness 的认证、在线消息及断线同步。
- [节点间协议](./protocol.md)、[集成与适配](./integration.md)：现有协议与接入文档；实施时须同步区分已支持能力与目标设计。

本文不改变上述规划的职责划分：通信回执不等于业务完成，节点可信不等于具体动作获准，移动端恢复不等于跨节点可靠投递。

## 2. 优先级与交付顺序

P0 表示正式承诺可靠执行或开放相应生产能力前必须补齐的基础，不阻止明确限制范围的隔离、只读试点。P1 表示紧随其后的产品可用性与恢复能力，P2 表示基础契约稳定后的扩展。

| 优先级 | 功能 | 首要收益 |
| --- | --- | --- |
| P0 | 结构化消息与统一执行事件 | 请求、增量输出及终态可解析、可关联 |
| P0 | Agent Adapter 可靠性 | 防止假成功、失控进程及无界资源消耗 |
| P0 | 消息、发现及本地接口安全 | 防止篡改路由、冒充属性及未授权调用 |
| P1，可独立并行 | 节点名称、labels 与展示 | 多节点可识别、可筛选，属性来源明确 |
| P1 | 持久状态、去重与恢复 | 断网、重启后可查询原状态，不盲目重做 |
| P1 | 文件安全交接与准确就绪状态 | 不把上传、进程存活误报为交接完成或能力可用 |
| P2 | 移动接入、事件回放及高级执行体验 | 在稳定契约上扩展客户端与恢复体验 |

建议按以下顺序实施：

1. 确定结构化请求和执行事件契约；同步修正成功判定，实现真正的流式 Adapter。
2. 并行交付本地节点别名、labels 与 CLI/TUI 展示；远端属性在发现通道加固后发布。
3. 完成完整签名、访问保护、有界并发、输出限制和进程生命周期管理，形成可控的在线链路。
4. 补齐持久状态、回执、去重、查询和文件接收凭据，再承诺相应可靠性。
5. 按产品需要增加事件回放、取消、移动接入及目标 OS 运维能力。

在线链路阶段的退出条件：可识别目标、实时看到输出、准确识别执行终态、失败不误报；未完成持久恢复时，明确不承诺可靠离线投递。

## 3. 数据格式与流式执行

### 3.1 实施前基础与差距（历史快照）

- 节点间已经使用 JSON，而非裸文本；`MessageEnvelope.Content` 仍是字符串，扩展内容放在 `Metadata`。
- Codex 使用 `--json`，OpenCode 使用 `--format json`；当前执行器通过 `cmd.Output()` 收集完整 stdout，之后才解析，未利用输出流进行实时转发。
- Adapter 外部接口一次返回一个结果，回信还会将 `runId` 拼入文本，不足以表达连续输出与执行阶段。

主要依据：`internal/protocol/messages.go`、`internal/natsbus/client.go`、`internal/adapter/adapter.go`、`internal/adapter/codex.go`、`internal/adapter/opencode.go`、`internal/messaging/handler.go`。

### 3.2 推荐格式分工

| 链路 | 推荐格式与处理方式 |
| --- | --- |
| Agent 到本地 Node | 通过工具、SDK 或受保护的本地入口提交结构化请求；Node 决定发送身份和受控路由 |
| Node 到 Node | JSON envelope；每条请求或事件对应一条 NATS 消息 |
| Node Adapter 到 Agent | 按产品能力转换成结构化请求或文本 prompt，网络签名等细节不交给 LLM 判断 |
| CLI 到 Node Adapter | 产品原生 JSONL/NDJSON 事件流，增量读取并转换为统一事件 |
| 大文件与产物 | 文件通道传输，普通消息只携带授权引用及完整性信息 |

NATS 已经提供消息边界，不需要在一条 NATS 消息中再装入持续增长的 JSONL。JSONL 是字节流的记录分隔方式，不是压缩格式，也不自动提供可靠性。

### 3.3 首批设计范围

- 按消息类型定义结构化 `payload`，不依赖解析自然语言判断受理或完成。
- 区分消息 ID、原请求关联 ID、执行 run ID、会话 ID；需要业务幂等时另行定义其范围和键。
- 请求消息 ID 可直接作为回复中的原请求关联，不机械增加值相同的重复字段。
- 定义少量统一事件：`run.started`、`run.output.delta`、`run.completed`、`run.failed`。
- 明确取消和结果未决的状态语义；连接中断或已经产生文本均不代表执行成功。
- 使用稳定错误码、失败阶段和必要诊断信息，避免仅返回自由文本异常。
- 增量事件携带 run ID 与序号，用于关联、去重和缺口检测；终态同样可关联。
- Adapter 屏蔽各产品的事件格式，不将产品原生 stdout 直接固化为公共协议。
- 显式区分允许发布的答案、进度与诊断信息，不默认转发工具参数、敏感路径或内部推理内容。

### 3.4 Agent-1 到 Agent-2 的处理示例

Agent-1 请求 Agent-2 分析日志，整体处理如下：

1. Agent-1 向 Node-1 的本地入口提交目标节点、目标 Agent、会话和任务正文。
2. Node-1 校验请求、生成消息 ID，以自身身份构造并签名 envelope，然后发布到精确的目标 subject。
3. NATS 检查连接与 subject 权限，向 Node-2 投递消息字节；不解释任务正文，不替 Node 验证业务授权。
4. Node-2 检查版本、签名、目标、权限、有效期及去重记录，将目标 Agent 映射到本地 Adapter。
5. Adapter 保存执行关联，把 `payload` 转为产品原生请求；若仅支持 prompt，则明确分隔任务指令与不可信输入数据。
6. Agent-2 输出原生事件流；Adapter 增量解析为统一事件，Node-2 添加网络字段及签名，逐条发布。
7. Node-1 按原请求与 run ID 接收结果；只有明确终态才能形成相应执行结论。

建议的请求 envelope 示意：

```json
{
  "protocolVersion": "v2",
  "id": "msg-101",
  "type": "task.request",
  "from": "node-1",
  "to": "node-2",
  "agentId": "log-analyst",
  "sessionKey": "session-17",
  "ts": 1792454400000,
  "expiresAt": 1792454460000,
  "payload": {
    "instruction": "分析日志，给出错误原因和排查建议。",
    "input": {
      "log": "ERROR database connection timed out"
    }
  },
  "sig": "<signature>"
}
```

以下仅展示对应增量事件的关联字段和正文；完整网络消息仍须包含版本、来源、目标、时间及签名：

```json
{
  "id": "evt-201",
  "type": "run.output.delta",
  "requestId": "msg-101",
  "runId": "run-88",
  "seq": 1,
  "payload": {
    "channel": "answer",
    "text": "日志显示数据库连接超时。"
  }
}
```

示例中的 `node-1`、`node-2` 是说明用标识，不替代当前密码学派生的真实 NodeID；签名占位值不是可验证凭据。`v2`、字段名及事件名需在详细协议设计中最终确定。

### 3.5 有界输出与流式验收

- 按字节阈值或短时间窗口合并小增量，不逐 token 发布；具体参数根据实测确定。
- 限制单个原生事件、单条网络消息、缓冲区和总输出大小，不能只依赖逐行读取器的默认限制。
- 独立、持续消费 stdout 和 stderr，避免阻塞；限制诊断留存和敏感内容暴露。
- 慢消费者策略必须明确：背压、输出转产物或停止并报错，不能无界缓存或静默丢弃答案。
- 验收：进程尚未结束时，对端已收到输出；大量输出不导致全量内存缓冲；部分输出后失败不会报完成；事件重复及序号缺口可识别。

暂不优先引入 Protobuf、压缩或自定义分片协议。先测量消息大小、频率、首字延迟和资源使用，再决定编码优化。

## 4. 节点名称与 labels

### 4.1 统一属性模型

采用 `labels`，不另建一套并行的 `cap.*` 能力标签；目标模型由保留键 `caps` 表达自报能力：

```json
{
  "displayName": "上海现场网关",
  "labels": {
    "env": "production",
    "role": "gateway",
    "caps": ["chat", "task.stream", "file.receive"]
  }
}
```

- `displayName` 用于可读展示，允许重名，不替代 NodeID/DID。
- labels 的值只允许字符串或字符串数组，不扩展为任意嵌套 JSON。
- 保留键固定类型，例如 `caps` 必须是字符串数组；能力标识有明确、稳定的含义。
- 数组按无序集合处理：去重、排序；空集合省略。签名使用统一规范化结果。
- 查询区分字符串精确匹配与数组成员匹配，不隐式拆分逗号字符串。
- 对键、值、元素数量及总大小设限；拒绝控制字符，输出时避免终端注入。
- 协议版本放在明确字段中，不混入任意标签；独立能力版本协商有实际需要时再设计。

现有 `capabilities` 的迁移须覆盖配置、广播、接收、展示和文档，通过显式版本规则完成切换，不能长期双写两套能力来源，也不能静默忽略旧节点的兼容性限制。

### 4.2 来源与安全边界

- 本地 alias、描述和 labels 独立持久化，不受远端心跳覆盖；本地与远端可复用属性类型，但来源必须保留。
- `caps` 是自报支持能力，不是当前就绪状态，更不是授权；不能把本地添加的标签当作对端能力证明。
- 远端名称和 labels 只有在发现通道具备签名、时效与重放保护后才发布和使用；签名覆盖整个声明，无需每个标签单独签名。
- 客户、位置和内部描述默认不全网广播，远端声明与本地备注应有不同可见范围。
- 首批标签用于筛选，不做隐式标签路由、通配 subject 或自动扇出。未来若支持选目标，必须解析为精确 NodeID，多匹配时失败关闭。

### 4.3 首批范围与验收

首批交付本地别名、labels、原子持久化，以及 CLI/HTTP/TUI 的展示和筛选。UI 同时展示可读名称与身份短指纹。

验收：同产品同版本节点可区分；重启和节点重新发现后备注仍保留；远端不能覆盖本地备注；重命名不改变身份与信任；非法标签被拒绝。

## 5. Agent Adapter 可靠性

流式输出必须与正确执行语义一起交付，不能只将 `cmd.Output()` 替换成逐行读取。

### 5.1 必须补齐

- 为受支持的产品版本定义成功、失败、异步接纳及终止事件契约；未知输出、登录提示、权限提示、空输出或仅启动事件不能被误判为完成。
- 联合检查退出结果与产品事件；非结构化 stdout 不静默回退为成功答案。
- 按目标 OS 管理进程树、等待上限、超时和取消；daemon 关停向在途执行传播取消。
- 超时或回复丢失可能发生在副作用之后，应标记结果未决，不对非幂等动作自动重跑。
- 有界消费 stdout/stderr；支持时通过 stdin 或原生请求 body 传正文，避免 argv 泄露及长度限制。
- 同会话执行串行，总并发、等待队列和资源占用有界。
- 本地 Agent 路由使用受控映射；不支持的 `agentId` 明确拒绝，不静默使用默认 Agent。
- 旧会话失效后创建新会话必须显式反馈上下文变化，不能静默丢失连续性。
- 固定受支持 CLI 版本与参数、事件契约；检查登录、权限和必要 Gateway 连接，不以可执行文件存在替代就绪。
- 修复 Codex Adapter 已有工厂分支但正常配置白名单拒绝选择的不一致，同步配置入口、展示和文档。

现有依据：`internal/adapter/`、`internal/messaging/handler.go`、`internal/config/config.go`、`internal/app/app.go`。

### 5.2 原生接口与 CLI 的取舍

若产品原生 HTTP/WS/SDK 提供稳定 run ID、状态查询、取消、幂等键和结构化事件，优先评估原生接口。没有这些保证时，换协议本身不提升可靠性。CLI 可以继续作为正式接入方式，但必须通过受支持版本的真实链路验收；不得用关闭 sandbox 或自动批准全部权限换取无人值守。

验收覆盖：未登录、权限拒绝、部分输出后失败、未知事件、超时、取消、超大输出、同会话并发和 daemon 关停；失败不假完成、不遗留失控子进程、不自动重复业务动作。

## 6. 通信安全底线

- 签名覆盖完整语义字段及 subject/用途域，排除签名本身；统一字段规范化、数字、空值、未知字段和版本处理规则。
- 接收端检查目标、权限、有效期与去重；签名正确不能替代这些检查。
- discovery announce 和 depart 均需身份保护与防重放；在线存活计算使用本地接收时间，并限制远端 TTL 和时间偏差。
- 本地发布、信任和配置接口使用访问凭据或受 OS 权限保护的本地通道；非 loopback 暴露须显式启用并保护。
- 接入 NATS 生产凭据、证书验证及 account/subject 权限，不以命名约定替代隔离。
- 默认不记录消息正文、凭据或工具敏感参数；保留关联 ID、阶段和错误码等必要审计信息。

实施前发现通道只校验公钥派生身份，depart 直接删除节点；本轮已补完整签名、时间和进程内防重放。部署层 ACL 仍需单独配置，不能用协议验签替代范围隔离。

验收：修改路由、属性、版本、有效期或正文被拒绝；旧声明重放和伪造 depart 不改变可信目录；未授权本地调用及跨范围访问被拒绝。

## 7. 持久状态、去重与恢复

### 7.1 先保证可查询，再承诺可靠性

- 持久保存请求、执行关联、关键阶段和最终结果，明确何时可以回复“已持久接纳”。
- 区分本地接纳、broker 持久化、对端接收、Adapter 接纳与业务完成，不用一个 `accepted` 或 `completed` 包办。
- 提供结构化回执和按原请求查询；去重记录与业务副作用的衔接必须有明确责任方。
- 进程重启后的未结束执行进入未决，通过产品或权威业务端查询；不直接重跑。
- 明确哪些请求允许离线恢复；时效敏感的审批、启动等请求不得在重连后自动补执行。
- 不承诺物理动作 exactly-once；通信去重不替代业务幂等。

### 7.2 精确续流按需增加

第一阶段可持久化关键状态与最终结果，不必永久保存每个 token。若要求断线后无缺口续流，再增加有保留期、配额和访问控制的事件日志，以及按 run ID 和序号补取、游标失效后的快照恢复。

Core NATS 不提供普通订阅的离线收件箱；JetStream 也不会自动补齐当前链路的接纳、幂等和恢复契约。

验收：双方进程或 broker 重启后可查询原请求；回执丢失不触发重复副作用；重复请求返回已有状态；过期动作不补执行；持久化失败不返回已持久接纳。

## 8. 文件交接、就绪状态与后续能力

### 8.1 文件交接

- 签名 manifest 绑定发送方、接收方、用途、内容指纹、大小和有效期。
- 验证 bucket/对象归属、目标路径、接收大小与空间配额；临时接收校验后原子交接。
- 区分上传成功、对端落盘和业务接收，保存持久接收凭据。
- 已落盘但 Adapter 通知失败时可恢复通知，不重复执行文件副作用。

现有 ObjectStore 读取已有存储层 digest 校验；目标是补齐发送方签名内容绑定，而非假定当前完全没有校验。

验收：内容替换、重复通知、超大文件、磁盘满、路径逃逸和重启不产生假完成或越界落盘。设备用途的文件交接是生产通道前置条件，不因通用路线图的实施顺序而降低优先级。

### 8.2 准确就绪与诊断

区分进程存活、NATS 在线、Agent 可执行、文件可用和承诺的投递保证；按操作所需能力判断就绪。提供积压、拒绝、过期、执行失败和输出超限等指标，结合请求/run ID 定位故障，不默认记录正文。

### 8.3 后续扩展

- 移动端：受限凭据、WSS、持久接纳、在线事件、同步与撤销的真实闭环；独立于跨节点恢复验收。
- 取消与流式体验：明确取消已接受、实际停止及结果未决之间的差别。
- Windows 或其他目标 OS：按实际部署验证服务权限、自动恢复、日志、升级与回滚。
- 暂不扩展自动调度、复杂 AgentCard、标签广播路由及更多 Adapter 数量；先稳定已有执行与通信契约。
