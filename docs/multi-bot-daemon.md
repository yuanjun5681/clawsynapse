# 单 Daemon 多 Bot 设计

最后更新：2026-10-31

## 1. 状态与结论

本文记录单 daemon 多 Bot 的设计约束与长期验收标准。**实现已落地，核心真实端到端场景及自动化边界检查已通过。** Bot Manager、独立 Runtime、分层配置、作用域凭据、本地 `/v2` 路径、显式 CLI 选择、内容存储及迁移/导出均已实现；当前使用方法以 [协议](./protocol.md)、[本地 API](./api.md)、[CLI](./cli.md) 和 [运维](./operations.md) 为准。下文保留原设计要求，不将一次环境验证扩大为所有平台、引擎和故障组合的保证。

2026-10-31 验证范围：

- 真实环境为 macOS、Docker NATS 2.11.9、单 daemon 的 A/B 和独立外部 Bot R。A/B 使用**两个 OpenCode 2.2 Binding**，模型均为 `zai-coding-plan/glm-5.3-flash`；不是两个不同引擎。
- 十一项真实端到端检查通过：独立 DID/ID；匿名/跨 Bot 访问拒绝和显式 CLI 选择；同一远端的信任/备注隔离；真实 OpenCode 原生 Session、工作目录和 v2 回复路由隔离；有界执行并发；停止 A 时 B 继续执行、A 重启后恢复自己的 Session/游标；Binding 切换与配置修订冲突；daemon 被 SIGKILL 后恢复期望状态、admitted 任务报告不确定且不盲目重跑；共享一个不可变实体但分别持有授权引用/可写副本、归档引用重启后保留；撤销 A 对 R 的信任不改变 B；归档 Bot 引用目录缺失时拒绝恢复与 GC、不重建空历史或删除实体。
- 真实 NATS 下另执行 8 轮并发启动/关闭/同进程重建压力检查，共接纳 96 次启动，验证关闭同步和 journal/runtime 释放。
- 实际 CLI 迁移、导出和导入验证保留原 ID、消息游标、信任、备注、自定义密钥/传输目录及无法重建来源的旧文件，备份及恢复后的引用实体可读。OpenCode 完成事件兼容性问题已修复，真实执行终态已验证。
- `go test ./...`、`go test -race ./...` 和 `go vet ./...` 已通过，自动化测试补充权限、状态、资源限制和恢复等边界行为。下文 17 项仍作为持续验收标准；不声称已对每个崩溃指令点、所有文件并发/回收交错、每个平台或其他 Harness 引擎执行穷举故障注入。

指导思想：

> Bot 是对外的协作身份，Harness 是背后的执行引擎。一个 daemon 可以托管多个 Bot，每个 Bot 绑定一个 Harness 接入。

主要决策：

1. `clawsynapsed` 是本地宿主进程，不是聊天身份，也不拥有代替所有 Bot 的公共网络身份。
2. 每个 Bot 独立持有身份密钥、DID、信任关系、消息状态、执行会话与本地备注。
3. 外部通过稳定 Bot 身份寻址；`displayName` 是公开名称，`localAlias` 是某个本地 Bot 对远端 Bot 的备注。
4. Harness 内部的 Agent、执行配置与 Session 不成为聊天联系人。ClawSynapse 不定义具体 Harness 产品的内部模型。
5. 每个 Bot 只有一个生效的 Harness 接入。多个 Bot 可以使用相同或不同产品；共享产品实例必须显式配置并满足隔离要求。
6. 共享进程不等于共享信任。一个 Bot 的批准、撤销或执行故障，不应改变另一个 Bot 的业务状态。
7. 首次实现采用每 Bot 独立 NATS 连接和运行上下文；共享管理入口，不先合并各 Bot 的发现、认证和消息状态。
8. 文件实体由 daemon 的不可变内容存储按摘要去重；每 Bot 独立持有传输记录、文件引用与授权，执行时按需生成工作副本。

## 2. 当前实现与改造依据

| 实现入口 | 已落地的结构 | 验证边界 |
|---|---|---|
| `internal/app/daemon.go`、`manager.go`、`app.go` | daemon 管理独立 Bot Runtime、生命周期、根目录锁与各 Bot 运行状态 | 共同进程故障域不变，不是强多租户安全沙箱 |
| `internal/config/daemon.go` | `schemaVersion: 2` daemon 配置与独立 Bot / Harness Binding 配置 | 不把身份作为可编辑配置字段 |
| `internal/api/daemon.go`、`cmd/clawsynapse/bots.go` | 管理 token / Bot token 分域、显式 Bot 本地路径和 CLI 选择 | 不恢复旧 `/v1` 默认 Bot 转发 |
| `internal/app/app.go`、`internal/messaging`、`internal/natsbus` | 每 Bot 独立身份、连接、Registry、信任、journal、consumer、Binding Session 与工作目录 | 保留已有持久 journal/outbox 与 wire v2，不退回纯内存收件箱 |
| `internal/blob`、`internal/transfer` | 共享不可变实体与每 Bot 的持久引用、传输记录、工作副本 | 内容去重不是信任或跨 Bot 文件授权；边界恢复仍需逐项验收 |
| `internal/migration` | 显式离线旧布局迁移，以及包含引用实体的单 Bot 私有导出/导入 | 不自动迁移、不自动换钥；代码落地不等于所有迁移恢复用例已验证 |

## 3. 术语与身份不变量

| 术语 | 定义 |
|---|---|
| Daemon | 托管多个 Bot 的本地进程，负责管理入口、配置与生命周期 |
| Bot | 可被外部寻址、认证并建立信任的长期协作身份，不等同于机器或进程 |
| Harness | 接收任务并执行工作的引擎；其内部组织方式不由 ClawSynapse 定义 |
| Harness Binding | 一个 Bot 到一个本地执行接入的配置关系，不是聊天身份 |
| Adapter | 在执行 seam 上把统一投递转换为具体引擎调用的实现 |
| Peer | 相对于当前本地 Bot 的已发现对端 Bot，不是另一个身份层级 |
| Conversation | 产品层的交流上下文，可映射到执行 Session，但本身不是联系人 |
| Harness Session | 执行引擎内部的上下文，不能作为 Bot 身份 |
| Blob | 按内容摘要标识的不可变文件实体；摘要不是访问凭据 |
| 文件引用 | 某个 Bot 对文件实体的持久关联，保存来源、文件名与访问授权；不是其他 Bot 的隐式授权 |

### 3.1 Bot 身份

沿用现有派生规则：Ed25519 公钥 → `did:key` → `n1-<hash>`。产品与新本地管理模型称该标识为 `botId`；其值与既有 `nodeId` 完全一致，不修改前缀或重新生成身份。

以下操作不得改变 Bot ID、DID 或已有信任关系：

- 修改公开名称、标签或本地备注。
- 停止、启动 Bot，或重启 daemon。
- 更换 Harness 接入或模型，重建执行 Session。
- 将完整 Bot 数据迁移到另一台设备。

新建 Bot 必须生成新密钥。复制配置不能复制身份；恢复原 Bot 必须显式导入其完整身份与状态。禁止在运行中同时启动同一身份的两个副本。

已有 Bot 的密钥缺失、损坏或公私钥不匹配时，启动失败，不自动生成替代密钥。生成密钥只允许发生在创建新 Bot 的事务中。

### 3.2 公开名称和本地备注

- `displayName` 来自 Bot 自身，通过签名发现消息公开；允许重名，不用于授权或路由。
- `localAlias` 归属于 `(本地 botId, 远端 botId)`，不在 Bot 之间自动共享，不向网络广播。
- 列表优先显示本地备注，其次公开名称，最后短身份标识；详情分别展示公开名称、备注和完整身份。
- 创建界面要求填写公开名称；导入的旧 Bot 可以暂时保留空名称并使用身份回退，不为补名字而生成新身份。
- 本地 Bot 选择只接受完整 ID，或由管理工具无歧义解析的 ID 前缀；名称检索不能隐式决定操作对象。

发现目录仍是运行态目录。已过期 Peer 的移除不代表用户删除了联系人；持久联系人簿是独立产品需求，不在本次托管改造中新增。

## 4. 运行架构与 Interface

### 4.1 模块职责

| 模块 | 职责 | 不承担的职责 |
|---|---|---|
| Daemon / Bot Manager | 管理目录、创建和加载 Bot、串行化生命周期、分发本地请求、聚合状态 | 代替 Bot 签名或共享所有 Bot 的信任判断 |
| 本地内容存储 | 校验、发布和读取不可变实体，去重、使用期保护及回收 | 按摘要自动授予访问权或暴露全局文件清单 |
| Bot Runtime | 身份、发现、认证、信任、消息、文件传输和该 Bot 的执行上下文 | 管理其他 Bot 或编排多个 Harness |
| Harness Adapter | 投递、状态检查、取消、会话映射、归一化执行结果 | 创建外部联系人或决定网络信任 |
| 本地 HTTP / CLI / TUI | 显式选择 Bot，检查凭据作用域，调用运行 Interface | 保存第二份身份或授权真源 |

在现有 `internal/app` 中拆分 daemon 宿主与单 Bot Runtime；不按每个领域再复制一层转发包装。复用现有 auth、trust、messaging、transfer 与 discovery 实现，向它们注入 Bot 专属依赖。

Bot Manager 的管理 Interface 围绕 `Create`、`List`、`Update`、`Start`、`Stop`、`Archive`、`Restore` 展开。业务入口通过已授权的 Bot 引用访问运行对象，不向调用方暴露可任意选择身份私钥的接口。

每次启动创建一份新 Runtime；停止后不复用已经关闭的 context、journal 或 Adapter。管理锁只保护状态和引用，不在全局锁内进行网络连接、执行探测或等待退出。同一 Bot 的生命周期操作串行，互不相同 Bot 的操作可以并发。

### 4.2 共享和独占资源

| daemon 共享 | 每 Bot 独占 |
|---|---|
| HTTP listener、管理身份校验、日志输出设施 | 密钥、身份、运行 context、NATS 连接 |
| Bot 管理目录、配置校验逻辑 | Registry、认证状态、信任和重放状态 |
| NATS 地址与 TLS 默认配置 | 消息 journal、outbox、cursor、consumer |
| 管理界面、进程资源预算、不可变文件内容存储 | Adapter、执行队列、Session 映射、工作目录、传输记录与文件引用 |

每 Bot 独立连接的理由：现有运行对象拥有连接关闭行为；连接还绑定 NATS 凭据。先保持隔离可以直接停止单个 Bot，避免一个 Bot 关闭共享连接或扩大另一个 Bot 的传输权限。

所有 Bot 可以使用同一服务器、同一共享消息 stream；连接凭据按 Bot 配置，不能因为同进程就自动获得其他 Bot 的 subject 权限。相同默认凭据只有在部署者明确允许时使用。共享 stream 的创建权限与运行期权限继续遵循 broker 部署约束，不能给每个 Bot 无限制管理权限。

全局配置故障、根目录锁冲突或管理 listener 失败使 daemon 启动失败。单个 Bot 的密钥、状态或连接初始化失败只使该 Bot 进入 `failed`，管理入口和其他 Bot 继续运行。

同一进程是共同故障域：进程崩溃、资源耗尽和同 OS 用户文件访问不提供强隔离。多 Bot 不是多租户安全沙箱。

## 5. 配置与持久化

### 5.1 配置分层

- **daemon 配置**：HTTP listener、TLS、管理凭据路径、数据根目录、日志、NATS 默认连接参数、全局资源预算及内容存储容量/回收策略。
- **Bot 配置**：公开名、标签、信任策略、一个 Harness Binding、执行超时、消息类型、文件限制、Bot 专属 NATS 凭据。
- **Bot 管理目录**：已注册身份、期望状态、当前配置修订号与归档状态；不保存运行时对象。

`botId` 从公钥派生，不是用户可编辑字段。目录名由派生 ID 决定，不接受公开名称或请求提供的任意路径。Webhook 等接入密钥使用受限凭据文件，不放进可回显的配置正文。

每个 Harness Binding 保留明确的 Adapter 类型和该类型所需参数，不引入与本项目无关的产品概念。相同产品类型可出现多次；不因此合并 Session 或工作目录。

### 5.2 建议目录

```text
~/.clawsynapse/
  config.json                  daemon 配置
  admin.token                  daemon 管理凭据
  bots.json                    持久 Bot 管理目录
  daemon.lock                  宿主独占锁
  blobs/
    tmp/                       在途下载与发布暂存，不对 Harness 开放
    sha256/
      <摘要前两位>/
        <完整摘要>             校验后发布的不可变文件实体
  bots/
    <botId>/
      config.json              Bot 配置与修订号
      credentials/             身份密钥、Bot 本地访问凭据及接入密钥
      trust.json
      replay-cache.json
      peer-attrs.json
      peers/
      state/messages.jsonl
      sessions/
      transfers/               持久传输记录、文件引用及授权，不存接收实体
      workspace/               按执行需要创建的可写工作副本
```

目录使用 `0700`，私钥、token 和状态文件保持现有受限权限及原子写入规范。日志带 `botId`，不输出 token、私钥或默认输出消息正文。不得通过符号链接或路径穿越把一个 Bot 的可写目录指向另一个 Bot。

Bot 创建流程：在临时目录生成身份并写入完整配置，派生 ID 并检测冲突，原子发布 Bot 目录，最后持久注册到管理目录。成功响应前完成所需文件及目录同步。崩溃留下的未注册目录不自动运行，也不覆盖；管理入口报告可恢复的未完成创建。

配置更新以修订号执行比较更新；冲突返回 `409`。单 Bot 配置是配置内容真源，管理目录只记录引用和期望状态，不复制整份配置。损坏或无法解析的持久文件应显式报错，不静默回退为空信任集或空消息库。

### 5.3 运行时配置变更

为避免半更新配置，运行中的 Bot 不允许直接修改执行、网络和信任配置，返回 `409 bot.must_stop`。停止后更新，下一次启动校验并完整装配。修改公开名同样遵循这条规则；后续若需要热更新，另行定义原子应用契约。

更换 Harness 不迁移或自动重放原引擎任务；旧 Session 保留为历史但不得直接交给新引擎恢复。Binding 有独立的本地修订标识，Session 存储作用域至少包含 Bot、Binding 和原有会话作用域。切回旧接入是否恢复旧 Session 必须显式选择，不能因产品名称相同就复用。

### 5.4 共享内容存储与文件授权

**建立信任不会同步文件，也不会创建副本。** 只有实际接收、导入或显式共享文件时，才建立该 Bot 的文件引用。同一内容被多个本地 Bot 接收时，共用一个不可变实体，但保留各自独立的来源、原文件名、传输 ID、接收时间和授权记录。

#### 接收与去重

1. 先按目标 Bot 验证传输权限及文件限制，将数据流写入 daemon 管理的暂存文件；不直接采用发送方的文件名或摘要作为本地路径。
2. 下载时计算 SHA-256 和实际大小，校验传输完整性与大小上限。发送方声明的摘要不能代替本地内容校验。
3. 由内容存储串行化同摘要的发布与回收。实体不存在时完成文件同步并原子发布；已存在时验证其完整性后复用，不覆盖不可变实体，也不暴露未完成下载。
4. 实体安全发布后，再原子持久化目标 Bot 的传输记录与授权引用；同一传输的重投不能重复生成引用或重复通知执行引擎。成功记录提交后才发送接收完成通知。

发布实体与 Bot 引用不依赖跨目录原子事务。崩溃可能留下无引用实体，由回收处理；不能留下已经宣告成功、却找不到实体的引用。实体缺失或损坏时显式报错，不把其他 Bot 的可写工作文件当成恢复来源。

去重只处理 daemon 本地物理存储，不改变 wire v2、按目标 Bot 的 Object Store bucket 或发送权限。分别发送给多个 Bot 仍可能产生多次上传和多份 broker 对象，不能宣称已经实现网络或 broker 去重。broker TTL 不自动撤销本地文件引用，也不清理工作副本。

#### 访问与 Harness 工作副本

- 内容存储只通过已授权的 `(botId, transferId)` 解析实体，不提供“知道摘要就能下载”的公共 Interface；也不允许通过枚举摘要或查询去重命中情况观察其他 Bot 的文件。
- 接收或管理员显式授权共享才可创建引用。仅因两个 Bot 互信，或实体已经存在，不得给另一 Bot 增加文件访问权。
- 每次通过本地 Interface 读取或转发文件，都检查 Bot 作用域凭据及有效引用；已授权的转发仍须通过正常网络传输和接收方授权流程。
- Harness 不直接获得全局 `blobs/` 路径或可写句柄。需要文件路径时，Adapter 在该 Bot 的 `workspace/` 中生成独立副本，并以该路径作为接收通知的 `localPath`；仅需数据流的接入可使用受 Bot 授权的读取入口，不必生成副本。
- 可写工作副本只在执行需要时创建，不能使用指向共享实体的可写硬链接或符号链接。修改只影响工作副本；重新发送时按实际修改后内容处理。

因此，多个 Bot 接收同一文件不会各存一份接收实体，但它们同时需要可写路径时，仍可能各有工作副本。这是可变执行数据的隔离成本，不在去重保证内。管理 Interface 的文件引用隔离不改变同 OS 用户和同进程缺少强安全隔离的事实。

#### 删除、回收与配额

- 删除某个 Bot 的传输记录，只解除该记录的授权引用，并按明确清理策略处理其工作副本；不能删除其他 Bot 的引用或直接移除共享实体。已复制到 Harness 的内容不能靠撤销引用追回。
- 只有持久引用为零、没有在途下载/发布、读取或工作副本生成占用的实体才可回收。归档 Bot 的引用仍有效；停止或归档不是释放文件的操作。
- 持久引用是真源，不以容易失配的内存引用计数决定删除。回收扫描必须覆盖停止和归档 Bot，与引用新增和在途占用互斥；记录损坏或恢复未完成时暂停相关回收，宁可保留多余实体也不误删。
- 进程恢复时先恢复注册 Bot 的引用和在途状态，再开始回收。备份及单 Bot 导出必须包含其引用指向的实体；仅复制 `bots/<botId>/` 不构成完整备份。
- Bot 配额按该 Bot 引用的不同实体大小计费，同一实体在多个 Bot 中分别占各自逻辑配额；重复传输记录不重复计入同一 Bot 的实体大小。工作副本和暂存有独立容量预算。daemon 同时限制去重后实体、暂存和工作副本的实际总占用，不能因为命中去重就绕过 Bot 配额。


## 6. Bot 生命周期

持久期望状态是 `running` 或 `stopped`；`archived` 另作为管理属性。运行状态如下：

| 状态 | 含义 |
|---|---|
| `stopped` | 身份与数据存在，无运行中的订阅和执行 |
| `starting` | 正在校验配置、加载状态、连接并建立订阅 |
| `running` | 网络接入已就绪；Harness 健康度单独报告 |
| `stopping` | 拒绝新业务操作，正在取消、落盘并释放资源 |
| `failed` | 本次启动或运行失败，保留错误阶段和身份数据 |
| `archived` | 停止且从活动列表移除，数据和身份保留 |

启动顺序：验证身份和独占权 → 打开 Bot 状态 → 创建 Adapter 与连接 → 准备认证、信任和消息入口 → 启动传输及发现 → 宣告可用。启动失败释放所有已创建资源，不保留半运行的 Runtime。

停止顺序：持久期望停止 → 阻止新本地业务请求及新执行接纳 → 在连接可用时尽力发送 depart → 暂停接收并取消执行 → 持久化终态或不确定状态 → 等待工作退出并关闭 journal → 关闭该 Bot 的连接并释放引用。

停止不得删除 durable consumer 或共享 stream，也不得清空未消费消息。已开始执行但无法确认完成的任务保留不确定语义；不能因重启或更换 Harness 自动执行第二次。Bot 停止期间 broker 是否保留消息仍受现有 stream 保留期约束，不承诺无限离线缓存。

生命周期调用先持久化期望状态，再返回 `202`；响应包含 Bot ID、期望状态和观察到的状态，调用方查询最终结果。重复 start/stop 为幂等；相反的过渡操作在正在转换时返回 `409 bot.transition_conflict`。崩溃后按期望状态恢复，不把中间运行状态当成已完成事实。

启动后的网络断开、Harness 不健康通过独立健康字段报告，不创建新身份、不自动切换引擎。失败状态允许管理员显式重试；daemon 重启可以重新尝试期望运行的 Bot，但不得盲目重试已接纳任务。

归档必须先停止，旧 Bot ID 不再对外运行；恢复后仍使用原身份。归档不是密钥销毁，也不是向所有对端自动撤销信任。永久擦除数据不包含在此管理 Interface 中，必须单独设计带显式确认的操作。

关闭 daemon 时先停止接收管理写操作，再按相同规则并发停止各 Bot，设置总体退出时限。超时退出后的任务通过现有 admitted 恢复规则标记不确定，不宣称已经安全取消外部副作用。

## 7. 消息、信任与 Harness 隔离

### 7.1 每个 Bot 都是完整网络参与者

- Bot A 对远端 R 的信任，不授予 Bot B 对 R 的信任；认证、待审批和撤销也分别维护。
- 发送身份来自请求路径所选且已授权的 Bot，正文不得覆盖发送者。
- 接收必须验证精确目标身份、subject、完整签名、时效和本 Bot 的信任状态。
- 同一 daemon 内 A 向 B 通信仍走正常签名、传输和授权路径，不引入绕过协议的内存捷径，也不默认互信。
- 本地观察到另一个 Bot 的存在不代表可以读取它的消息、文件或 Session。

### 7.2 执行绑定

外部发送给 Bot；Bot 使用唯一配置的 Binding 投递，不按公开名、远端任意 metadata 或消息正文选择另一个 Harness。

保留通用 Adapter 已有的可选 `agentId` 提示及本地允许列表语义，不把它复用为 Bot ID 或 Harness 选择器，也不把允许列表发布成联系人目录。本次不扩展 Agent 级网络身份或授权。

外部对话关联键与 Harness 原生 Session 分开。Session 隔离至少包含接收 Bot、Binding、发送 Bot 和外部会话作用域；不同 Bot 接收同一发送方的同名会话键不能碰撞。Webhook 共享实例必须可靠区分接收 Bot，并自行落实执行权限和上下文隔离。

多个 Bot 指向同一个 Harness 实例属于显式共享执行环境，不构成独立沙箱。Adapter 必须能隔离或验证 Session、工作目录与身份上下文；无法保证时，管理校验拒绝共享绑定，而不是声称按配置名称就已隔离。

### 7.3 资源控制与状态

每 Bot 配置有界并发、排队和文件逻辑配额，daemon 再施加全局执行预算、文件物理容量预算及有界公平调度；文件计费和回收遵循第 5.4 节。等待全局配额的任务仍可取消并再次检查时效。单 Bot 队列不能无限占用全局执行槽或内存。

Bot 网络在线和 Harness 可执行分别报告。单个 Harness 探测失败不停止其他 Bot；执行请求按既有结构化错误返回，不静默投递给其他后端。

## 8. 本地管理与访问权限

### 8.1 两类凭据

| 凭据 | 权限 |
|---|---|
| daemon 管理凭据 | 创建、列出、配置和管理所有本地 Bot；可明确选择 Bot 进行管理操作 |
| Bot 作用域凭据 | 只访问一个指定 Bot 的身份、对端、消息、请求、信任和传输操作；不能管理其他 Bot 或改变绑定 |

每个凭据在服务器端绑定权限与 Bot ID，不能由请求正文自报作用域。现有全局管理 token 不分发给 Harness。Bot 凭据轮换只改变本地访问权限，不改变 Ed25519 身份。

HTTP listener 继续遵守默认 loopback、远程显式开启、TLS 和请求大小限制。配置读取须去除密钥与 token。日志中不能记录 Authorization。

同 OS 用户能够读取同一进程拥有的凭据文件，因此此处提供的是管理 Interface 的最小权限，不是对恶意同用户进程的安全隔离。

### 8.2 建议 HTTP Interface

新增本地 `/v2` 管理 Interface，保持现有 `types.APIResult` 的封装、稳定 code 与 `ts` 约定。

| 端点 | 作用 |
|---|---|
| `GET /v2/health` | daemon 状态与活动/失败 Bot 数量；不代替逐 Bot 健康 |
| `GET /v2/bots` | 管理员列出本地 Bot |
| `POST /v2/bots` | 创建 Bot，默认停止；返回 `201` 与派生身份 |
| `GET /v2/bots/{botId}` | 查看身份、期望/运行状态和接入健康摘要 |
| `PUT /v2/bots/{botId}/config` | 停止状态下按修订号替换配置，成功 `200` |
| `POST /v2/bots/{botId}/start`、`stop` | 管理生命周期，返回 `202` |
| `POST /v2/bots/{botId}/archive`、`restore` | 归档/恢复，恢复后默认停止 |
| `/v2/bots/{botId}/peers` | 查询该 Bot 视角的远端目录和本地备注 |
| `/v2/bots/{botId}/auth/...`、`trust/...` | 该 Bot 的认证与信任操作 |
| `/v2/bots/{botId}/publish` | 以该 Bot 身份发布消息 |
| `/v2/bots/{botId}/messages`、`requests/{messageId}` | 查询该 Bot 的消息游标和请求状态 |
| `/v2/bots/{botId}/transfer/...`、`transfers` | 该 Bot 的传输记录、授权文件读取、发送及引用删除操作；不暴露全局实体路径 |

原单 Bot 业务端点迁到显式 Bot 路径，完整保留原操作集合，不只实现表中示例。对端本地视图使用 `botId`，发送目标使用 `targetBot`；不同时接受新旧字段别名。未知 Bot 返回 `404`；合法凭据访问其他 Bot 返回 `403`；停止状态的运行操作返回 `409`；参数错误返回 `400`。停止 Bot 的已落盘消息和信任查询仍可用，但新发送、审批等运行状态变更必须先启动。

归档返回 `200` 前已持久化且确认无活跃 Runtime；转换尚未结束返回 `409`。本地请求进入 Bot Runtime 前获取生命周期引用，停止须等待引用释放，避免请求与资源关闭竞争。

### 8.3 CLI 与 TUI

建议新增 `clawsynapse bots` 和 `clawsynapse bot create|start|stop|archive|restore`。业务命令统一显式指定 `--bot <botId>`，例如：

```text
clawsynapse --bot <local-bot-id> peers
clawsynapse --bot <local-bot-id> publish --target <remote-bot-id> --message "hello"
```

不得在缺少选择时自动使用“第一个 Bot”；即使当前只有一个 Bot，也使用同样规则。Bot 作用域凭据可以绑定本地选择，显式指定不同 Bot 时直接拒绝。

TUI 区分本地 Bot 列表和当前 Bot 的远端 Peers；页面持续显示当前身份。切换 Bot 时清空或按 Bot 隔离缓存、分页游标、详情、过滤与异步请求结果，防止旧响应覆盖新页面或将操作发给错误身份。

## 9. 命名、协议与现有文档

产品层将 Node 称为 Bot；daemon 不再被当作单个 Bot。`Peer` 仍可作为对端关系术语保留。

**本次设计不修改现有网络 v2 字段名称或身份算法。** 网络中的 `nodeId`、subject、签名编码、消息 `from/to`、durable consumer 名称继续使用既有契约。新本地模型的 `botId` 在协议编码 seam 映射到已有字段，不增加第二套可独立赋值的身份，也不在同一网络消息中重复发送 `botId` 和 `nodeId`。

原因：单 daemon 多身份不要求全网同时升级；仅为产品改名而重写签名结构和 consumer 标识会引入无关迁移风险。若未来要求网络字段也全面改名，应单独升级协议版本并协调所有调用方，不能通过严格 v2 解码的隐式兼容实现。

稳定文档已随本地契约切换同步更新；以下仍是各文档必须覆盖的职责：

- [总览](./overview.md)、[概念](./concepts.md)：从单 daemon 单身份改成宿主与 Bot 分层。
- [集成](./integration.md)：每 Bot 一个 Harness 接入、Bot 作用域凭据和调用路径。
- [API](./api.md)、[CLI](./cli.md)、[运维](./operations.md)：新配置、显式选择与生命周期。
- [协议](./protocol.md)、[信任](./trust.md)：说明 Bot 与既有 wire node 身份的关系及信任作用域。
- [Agent Internet](./agent-internet.md)：内部 Agent 不与对外 Bot 身份混用。
- [移动接入规划](./mobile-nats-access.md)：替换“一个 Node 承载多个逻辑 Bot”的旧定义。移动设备的用户凭据仍不等于 Bot 身份或本地管理权限。

上述文档描述当前实现契约；完整行为验收状态以第 1 节的证据与缺口为准，不以文档更新本身作为实现正确性的证明。

## 10. 单 Bot 安装迁移

采用显式、停机、可回滚的格式迁移，不在正常启动时猜测旧目录并自动创建新身份。

1. 停止旧 daemon，取得旧数据根目录独占权，检查迁移空间与文件权限，记录配置版本和迁移清单。
2. 验证原公私钥，计算原身份；密钥不可用时终止，不生成替代身份。
3. 将旧全局配置拆为 daemon 配置和一个 Bot 配置。保留原身份、公开名、信任策略及 Adapter 绑定。
4. 在暂存布局完整迁移信任、待审批、重放、备注、消息 journal/outbox、游标、执行 Session 和传输状态。接收文件经实际内容校验后导入共享内容存储，重复内容只导入一次，并为原 Bot 持久建立各自传输记录和授权引用。现有传输索引仅在内存中，迁移工具需结合可用记录、文件名与持久通知重建；无法确定的来源标为未知，不伪造授权历史，也不丢弃未能关联的文件。自定义目录与密钥路径必须纳入清单，不只迁移默认目录。检查持久绝对路径并明确重写映射；需维持 Harness 路径的文件转为该 Bot 的独立工作副本，不指向全局实体。单独迁移/导出 Bot 时，打包所有被引用实体并在目标端校验后重建引用。
5. 原子发布新布局及管理目录，以迁移完成标记作为提交点。原数据备份不删除；提交前崩溃可重试，未提交的新目录不得启动。
6. 生成新的管理员/Bot 作用域凭据，旧单 Bot token 不自动升级为新的全局管理权限。更新 Harness、CLI、TUI 与其他本地调用方的路径及凭据。
7. 新 daemon 启动原 Bot，继续使用相同网络 ID、inbox 和 durable consumer。已接纳未完成任务遵循当前不确定恢复语义，不自动重做。

本地 `/v1` 单 Bot 业务入口在切换时移除，不保留默认 Bot 转发兼容层；新旧配置不能混用。此次是本地管理契约切换，不要求远端 Bot 同时升级网络协议。

只有在新布局尚未接收消息或执行任务前，才可直接恢复备份回滚。产生新状态后不能直接覆盖旧备份，必须停止并显式迁回新数据；任何时候不得同时启动新旧身份副本。

## 11. 实施顺序与验收

### 阶段一：提取单 Bot Runtime

从当前 `App` 中分离宿主管理和 Bot 运行，保留单个 Bot 的行为；引入可等待的停止、每 Bot 状态根目录和独占校验。移除领域模块对 daemon 全局配置与全局连接的隐式依赖。

### 阶段二：多 Bot 管理与隔离

实现管理目录、创建/配置/启动/停止/归档/恢复、每 Bot 连接和资源控制；交付共享不可变内容存储、持久文件引用、授权读取、工作副本与安全回收。接入管理员及 Bot 作用域凭据，再开放显式 Bot 路径，避免出现“已有多 Bot，但授权仍全局共享”的中间交付。

### 阶段三：工具与迁移切换

更新全部本地调用方、TUI、配置与运维说明，交付完整迁移工具；删除旧单 Bot 路由与隐式选择。协调本地契约升级，不改变 wire v2。

### 必须通过的行为验收

1. 一个 daemon 创建并同时运行 A、B；外部观察到不同 DID/ID，分别向其发送消息，只到达各自绑定的 Harness。
2. A 信任 R、B 不信任 R：R 只能按各自信任状态通信；撤销 A↔R 不改变 B。
3. 相同发送方、消息 ID、外部会话键到达 A/B，消息去重、cursor、幂等键、执行 Session、文件引用和工作副本均不串用；共享实体不构成共享访问权。
4. 同一个远端在 A/B 中可以具有不同 `localAlias`，心跳不覆盖备注，备注不广播。
5. 停止、启动、归档或破坏 A 的配置，不中断 B 的连接、工作和管理访问；相同身份不能被重复加载。
6. A 的作用域凭据不能发布为 B、读取 B 消息、修改 B 信任或调用 daemon 管理操作；正文伪造身份无效。
7. daemon 崩溃后恢复所有期望运行的 Bot；未终结 admitted 执行不盲目重跑，broker consumer 和本地 cursor 连续。
8. Bot 名称重复或修改不改变路由；遗漏本地 Bot 选择不执行任何操作。
9. 更换 Harness 后不错误恢复原引擎 Session；未确认完成的旧任务不会在新引擎重放。
10. 缺失/损坏身份、目录锁冲突、创建事务中断和配置修订冲突均显式失败，不能静默生成身份或覆盖数据。
11. 旧安装迁移后 ID、信任、备注、消息及传输状态保持；旧远端无需升级即可继续通信。
12. 实际启动单 daemon、两个不同执行接入与一个外部 Bot，观察上述收发、停止隔离与重启恢复；不能仅用 mock Adapter 测试代替端到端验收。
13. 同一内容分别发送给 A/B，本地只有一个不可变接收实体，但各有独立记录与授权；仅建立信任不增加文件引用。不同目标的 broker 副本不在本地去重保证内。
14. 无引用的 Bot 即使知道内容摘要也无法读取、转发或查询其他 Bot 的文件存在性；删除 A 的引用不影响 B，归档 B 仍保留其引用。
15. A/B 的工作副本可独立修改，原实体和另一 Bot 的内容保持不变；Adapter 不向 Harness 提供全局实体路径或可写硬链接。
16. 并发接收相同内容、下载中断、实体发布后引用提交前崩溃、读取与回收竞争均不产生可见半文件或误删；损坏引用阻止不安全回收。
17. 验证每 Bot 逻辑配额、工作副本/暂存预算和全局物理容量；去重命中不能绕过授权或配额。单 Bot 导出恢复后所有引用可解析，旧文件迁移不丢失无法重建来源的实体。

永久测试持续覆盖身份隔离、权限、状态转换和恢复等可见行为，并保留真实 daemon/CLI 场景。第 1 节记录已通过的核心端到端与自动化检查范围；上述要求不因一次验收而删除，也不代表所有故障组合已穷举。两个同产品的独立 OpenCode Binding 满足“两个执行接入”，不能写成两个不同引擎。
